# MiniMind: обучение диалогу с переменной ролью

**Последующая проверка пользователем выявила повторяемый цикл с присвоением
имени Sofia модели.** Ошибка есть и в исходной базе в иной форме; очистка
истории не делает ответы правильными. См. [диагностику](sofia-loop-diagnosis.md).
Checkpoint пока не годится для разговорного персонажа.

17 октября 2026. Первый ограниченный опыт на MiniMind2-Small, 25 829 888
параметров. Исходная revision: `8c0c0de640cd532fee03d329b95a58c56591b5bc`.
Это full-parameter SFT с правильными ответами в тексте, а не дистилляция
вероятностей большой модели. Нового pruning или квантования в этом опыте нет.
Прошивка ESP32 не меняется; работоспособность и скорость на плате не проверены.

## Данные и границы проверки

- 1 400 коротких общих инструкций и разговоров из
  [Smol-SmolTalk](https://huggingface.co/datasets/HuggingFaceTB/smol-smoltalk/tree/f73fe857d519ff6ac5af2ea67c4d3834da7b8bcc).
  Один закреплённый shard; до трёх первых полных пар, до 40 слов в сообщении.
  Это автоматический фильтр, не полная ручная проверка качества корпуса.
  Фактическая смесь: openhermes 521, constraints 355, rewrite 271, magpie 253.
  Здесь много форматирования и перефразирования; это ограниченная замена
  полноценному корпусу повседневных многоходовых диалогов.
- 1 600 разговоров с детерминированными правильными ответами: разные имена,
  животные и предпочтения в system prompt; имена пользователя, коррекции,
  друзья, принадлежность предметов, отрицание и неизвестные факты.
- Валидация: 150 общих и 200 контролируемых разговоров. Общие разговоры
  разделены по хешу нормализованного первого вопроса; контролируемые используют
  отдельные имена. Нельзя утверждать, что эти имена отсутствуют в публичном
  корпусе или исходном pretraining.
- В контролируемой части нет драконов и Ember. Проверка переноса роли использует
  четырёх драконов, другие имена и формулировки. Это перенос в близком семействе
  шаблонов, а не доказательство общего понимания произвольных инструкций.
- `dialogue-v1.json`: 36 строгих проверок короткого ответа и четыре свободных
  диалога. Неверный формат считается провалом даже при верном факте; этот
  показатель не равен качеству разговора.
- `compression-v1.json`: отдельные 12 естественных сценариев с ранее записанной
  рубрикой. `retention-v1.json`: маленькая дополнительная проверка общих знаний,
  подготовленная во время обучения до просмотра её исходных ответов.
  После этого опыта все эти тесты становятся development-наборами.

Общая смесь помогает следить за сохранением навыков, но не гарантирует отсутствия
забывания. KL-регуляризация относительно исходной модели не применялась.
Данные публичного корпуса синтетические; локальный Qwen в этом опыте не
генерировал новые ответы. Источники и хеши: [provenance](../training/dialogue-v1/provenance.json).

## Обучение

Mac GPU MPS, FP32, 3 эпохи, batch 8, AdamW, начальный learning rate `5e-5`,
cosine до 10%, weight decay 0.01, clipping 1, seed 42. Контекст 256 токенов.
Обучаются только токены ответа ассистента и EOS; вопросы и padding маскируются.
HF сдвигает labels внутри функции loss — повторного сдвига нет. Старые полные
пары истории удаляются при нехватке места; system и последний вопрос сохраняются.

После токенизации: 4 160 ответов, 81 606 supervised tokens за эпоху; 493 ответа
валидации. Семь обучающих и один проверочный ответ не поместились в контекст.
Лучший checkpoint выбирается по token-weighted validation loss, не по тестам.

## Воспроизвести

Окружение: `tools/requirements-dragon.txt`. Исходную модель скачать по инструкции
в [dialogue-candidates.md](dialogue-candidates.md). Чтобы пересобрать сохранённые
JSONL, дополнительно скачать один shard:

```python
from huggingface_hub import hf_hub_download
from pathlib import Path
hf_hub_download("HuggingFaceTB/smol-smoltalk",
    repo_type="dataset", revision="f73fe857d519ff6ac5af2ea67c4d3834da7b8bcc",
    filename="data/train-00000-of-00004.parquet",
    local_dir=Path.home()/".cache/tinyml-smol-smoltalk")
```

```sh
python tools/prepare_dialogue_data.py
python -m unittest discover -s tools -p test_dialogue_train.py
python tools/dialogue_train.py train \
  --model "$HOME/.cache/tinyml-minimind2-small" \
  --output build/dragon/dialogue-v1 --device mps
python tools/dialogue_train.py eval \
  --model build/dragon/dialogue-v1/best \
  --output build/dragon/dialogue-v1/evaluation.json
bash tools/dragon_chat.sh dialogue-plain
```

Для CPU заменить `--device mps` на `--device cpu`. Существующий каталог run
перезаписывать нельзя: для повторного обучения выбрать другой `--output`.
Веса находятся локально в `build/dragon/dialogue-v1/best`, в Git не включены.
На другом компьютере один `git pull` не скачивает обученные веса.

Тесты проверяют маску ответов/EOS/padding, совпадение HF loss с ручным causal CE,
разделение идентификаторов и правильное соответствие имён в учебных диалогах.

## Первый результат и второй опыт

Первый run завершён: 254 секунды, выбран epoch 3. Общая validation loss снизилась
с 2.534 до 2.009, но general loss выросла с 2.571 до 2.854. Почти нулевая ошибка
на контролируемой валидации оказалась плохим предсказателем переноса на новые
формулировки: строгая проверка дала лишь 2/36 вместо исходных 0/36. Все 68
ответов завершились по EOS вместо исходных 47/68, что говорит о формате, а не
о содержательном улучшении.

Примеры первого run:

- `My name is Bram` → `Hello, Bram!`; исправление на Vera →
  `Thanks for correcting me, Vera.`; затем `Your name is Vera.`
- `The pear is mine. The apple is yours.` →
  `You have the pear. I have the apple.`; вопрос о фрукте пользователя →
  `The pear is yours.`
- На просьбу представиться: `Welcome to Ernstole. I'm Ernstochia. What's your first mind?`
- В нейтральном контроле `1 + 1` → `2 + 1 is 1 + 1 = 4.`; исходная модель
  давала правильное значение 2, хотя не соблюдала требование короткого формата.
- Факт `The capital of France is Paris.` сохранился. Два факта — слишком мало,
  чтобы оценить сохранение общих знаний в целом.

Повторная загрузка весов дала validation loss 2.009422 на CPU против 2.009426
на GPU перед сохранением. Это исключает крупную ошибку сохранения как объяснение
наблюдаемого результата. В знакомом шаблоне отдельный пример с Wade и Mina
после загрузки ответил верно: `I am Wade. You are Mina.`

Из-за переноса и забывания проведён второй run **с исходной модели**, на той же
смеси и seed: LR `1e-5`, 3 эпохи, KL(base || student) с коэффициентом 1 и
температурой 1 на токенах ответов **общих** заданий. Контролируемая часть получает
обычный CE. В отличие от большого Qwen, исходная MiniMind имеет тот же
токенизатор, поэтому здесь доступно прямое сопоставление вероятностей токенов.
Reference заморожена; это защита исходного поведения, включая его слабости.
Одновременно изменены learning rate и регуляризация, поэтому данный опыт не
позволяет приписать разницу только KL; для этого нужна отдельная ablation.

Для второго run checkpoint допустим только при general validation loss не выше
исходной более чем на 5%; среди допустимых выбирается минимальная общая loss.
Этот порог относится к среднему loss, а не гарантирует сохранение каждого факта.
Второй опыт выбран после просмотра первого, поэтому повторные тесты —
development-проверки, не новая независимая оценка.

```sh
python tools/dialogue_train.py train \
  --model "$HOME/.cache/tinyml-minimind2-small" \
  --output build/dragon/dialogue-v1-retained --device mps \
  --lr 0.00001 --reference-kl 1 --general-loss-tolerance 0.05
```

Дополнительный unit test проверяет направление KL, маску general/assistant и
отсутствие градиента на исключённых позициях.

## Итог двух запусков

| Проверка | Исходная | SFT, LR 5e-5 | SFT + KL, LR 1e-5 |
|---|---:|---:|---:|
| Общая validation loss | 2.534 | 2.009 | 1.671 |
| General validation loss | 2.571 | 2.854 | 2.371 |
| Строгие ответы в нужном формате | 0/36 | 2/36 | 2/36 |
| 1 + 1, по смыслу | 2 | неверно | 2 |
| Столица Франции, по смыслу | Paris | Paris | Paris |

Второй run занял 308 секунд, выбран epoch 3. Несмотря на улучшение loss,
пригодного свободного разговора не получилось. В естественных сценариях
у второго варианта явно удачны 3/12 финальных ответов: исправленное имя Vera,
зелёный как предпочтение пользователя и груша как его фрукт. У первого также
3/12 явных успеха, но вместо цвета — признание неизвестного местоположения.
Финальные ответы оценены самим coding assistant по заранее записанной рубрике;
это маленькая необъективизированная диагностика, не независимый benchmark.

Роль дракона не удерживается: на просьбу представиться второй вариант повторяет
вопрос; при различении Tomas и Ember присваивает имя Tomas себе. История про
потерянную шляпу зацикливается. На вопрос об имени друга он часто отвечает
правильным предложением, но не соблюдает формат одного имени. Поэтому строгие
2/36 не описывают весь прогресс, однако просмотр полных ответов также не даёт
оснований считать модель хорошим собеседником.

Снижение общей validation loss не означает сохранения всех знаний. Щадящий
вариант сохранил два проверенных исходно правильных факта, но исходная база
слишком слаба для широкой оценки забывания. Контролируемая валидация использует
те же шаблоны с другими значениями и переоценивает практическое качество.
Для следующего опыта нужны более разнообразные разговоры и перефразирования
в отдельных validation-семействах; возможно, потребуется другая английская база.
Продлевать текущие шаблоны на много эпох оснований нет.

На этом Mac можно сравнить оба результата:

```sh
bash tools/dragon_chat.sh dialogue        # меньший LR + KL
bash tools/dragon_chat.sh dialogue-plain  # первый SFT
```

Веса второго: `build/dragon/dialogue-v1-retained/best`. В Git сохранены код,
данные и отчёты; веса остаются на Mac. Это локальные HF-модели, не новые
готовые бинарники для ESP32. Нет оснований обещать им 10 токенов/с на плате.
