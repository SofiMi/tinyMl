# Сжатие Supra2 100M Q4: zstd и LZ4

Дата UTC: 2026-10-18T15:54:48Z. Весь исходный GGUF: **67,102,400 байт** (63.994 МиБ).

SHA-256: `b920477b6de0b1d89536f51fe20fc3e96727bf5f73f2a239e8945d25b9469361`.

## Выводы

Все 100 вариантов завершены, каждый сохранённый файл распакован и совпал
с исходником по SHA-256. Суммарно локальные артефакты занимают 6 590 478 213
байт в `build/compression-supra-q4/artifacts/`; в Git их нет.

- Лучший размер во всём опыте: **zstd 10, целиком — 65 423 443 байта**, экономия
  1 678 957 байт (2,502%). Это по-прежнему 62,393 МиБ, далеко за пределами 16 МиБ flash.
- Лучший LZ4: **уровень 9, чанки 512 КиБ — 66 287 827 байт**, экономия 1,214%.
  Это всего на 2794 байта меньше, чем LZ4 9 целиком. На этом входе уровень 10
  дал больший файл, чем уровень 9; размер не обязан монотонно уменьшаться.
- У zstd чанки 512 КиБ прибавили только 10 942 байта к лучшему целому файлу.
  Чанки 64 КиБ прибавили 72 519 байт. Для адресного чтения цена разбиения по
  размеру здесь невелика, но это не подтверждает скорость inference с распаковкой.
- LZ4 9 распаковал целый файл за медианные 0,0163 с, zstd 10 — 0,0337 с на этом
  Mac. Это не скорость ESP и не стоимость чтения с SD/flash. Упаковка файла
  сама по себе не уменьшает размер распакованных весов в оперативной памяти.

Дополнительно штатные CLI `zstd -t` и `lz4 -t` проверили лучшие **целые**
файлы. Пользовательский формат чанков проверен скриптом по индексу и SHA-256.

## Методика

- Сжимается весь GGUF, включая токенизатор, метаданные и тензоры; это не дополнительное квантование.
- Уровни 1–10 обоих алгоритмов. У LZ4 уровни 1 и 2 используют одинаковый быстрый режим; с 3 начинается HC.
- Размеры чанков — 64/128/**254**/512 КиБ, 1 КиБ = 1024 байта. 254 не заменено на 256.
- Каждый чанк — отдельный frame без общего словаря и зависимости от предыдущего чанка.
- Оба формата сохраняют размер исходных данных и checksum. LZ4: linked blocks внутри frame, максимум блока 4 МиБ.
- Целый файл — обычный .zst/.lz4. Чанки — контейнер .tmlc: 24 байта заголовка и (N+1) × 8 байт индекса, затем frames.
- В таблицах размер фактического файла **включает заголовки frames и индекс контейнера**.
- Время — медиана 3 последовательных проходов в памяти, включая создание codec context и Python-обёртку; без дискового I/O, хеширования и сравнения результата. Один поток, без параллельных запусков этого benchmark.
- Все повторы распакованы и побайтно сверены; каждый сохранённый файл отдельно прочитан с диска и проверен SHA-256.
- Это измерения Mac, не ESP. Скорости зависят от машины и текущей нагрузки; небольшие различия времени незначимы.

Среда: `macOS-26.2-arm64-arm-64bit`, Python 3.10.19, zstandard 0.25.0 / libzstd 1.5.7, lz4 4.4.5 / liblz4 1.9.4.

Размер % = размер результата / исходный размер × 100. Экономия % = 100 − размер %.
Скорость распаковки = исходные МиБ / секунды распаковки. Все замеры также есть в [CSV](results.csv) и [JSON](results.json).

## Ограничения для ESP

Размер сжатого файла — расход накопителя, не измерение RAM. Для вычислений веса нужно распаковывать; чанки позволяют делать это частями, но требуют отдельного загрузчика и интеграции с inference kernel. Текущий GGUF-движок не читает этот экспериментальный контейнер.

Размер чанка не является полным бюджетом RAM: дополнительно нужны входной буфер, состояние декодера, вычислительные буферы, активации и KV-кэш. Их использование на ESP и влияние на токены/с здесь не измерены.

## Повторение

```sh
python3 -m venv build/compression-venv310
build/compression-venv310/bin/pip install 'zstandard==0.25.0' 'lz4==4.4.5'
build/compression-venv310/bin/python tools/benchmark_model_compression.py \
  --input build/model-playground/supra/Supra2-100M-Instruct-Q4_K_M.gguf \
  --output build/compression-supra-new --repeats 3
```

Выходной каталог должен быть новым. Артефакты сохраняются в его подкаталоге `artifacts/`; их имена и SHA-256 перечислены в CSV/JSON. В Git передаются скрипт и отчёт, без гигабайтов архивов.

Формат .tmlc: little-endian `<8sIIQ>` = magic `TMLCMP01`, codec (1=zstd, 2=lz4), размер чанка, исходный размер. Число чанков N вычисляется округлением вверх; далее N+1 uint64-смещений относительно начала payload. Последнее смещение равно длине payload.

Документация: [LZ4 frame](https://python-lz4.readthedocs.io/en/stable/lz4.frame.html), [zstandard](https://python-zstandard.readthedocs.io/en/latest/compressor.html).
