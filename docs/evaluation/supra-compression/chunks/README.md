# Разбор отдельных чанков Supra Q4

Анализ существующих 80 контейнеров: два алгоритма, уровни 1–10, четыре размера чанка. Их SHA-256 повторно сверены с исходным benchmark; повторного сжатия не было. Распаковка всех файлов проверена в [основном опыте](../README.md).

Количество тензоров в GGUF: 134. Область данных тензоров начинается с байта **1,171,136**; всё до неё — заголовок, метаданные, описания тензоров и выравнивание. Исходник проверен по SHA-256.

## Лучший уровень для каждого размера

Главное наблюдение: при 64 КиБ LZ4 уровня 9 увеличивает 1004 из 1024 чанков;
zstd уровня 10 — 452. Внутри области тензоров общая экономия zstd составляет
1,19–1,23% в зависимости от размера чанка, а LZ4 практически нулевая
(от −0,013% до +0,008%). Чистые чанки метаданных сжимаются значительно лучше:
на 65–74%. Это объясняет, почему общая экономия GGUF выше, чем экономия
его основной области весов.

Из проверенных размеров 512 КиБ даёт наименьшие файлы у обоих алгоритмов.
Если важнее меньший распакованный участок, zstd с чанками 64 КиБ теряет
лишь 61 577 байт относительно zstd с чанками 512 КиБ. Однако 64 КиБ — размер
выходного участка, а не полный расход RAM декодера или модели.

Можно хранить увеличившиеся чанки без сжатия, если добавить признак raw/frame
в формат. Но даже верхняя оценка выгоды мала: максимум 27 108 байт среди всех
80 конфигураций. Суммы расширений сохранены в `total_expansion_bytes` таблицы
`all-levels.csv`; расходы на новый индекс
и признаки ещё пришлось бы учесть. Текущий формат не изменён.

Итоговый файл включает индекс. Размер отдельного чанка включает заголовок и checksum frame, но не индекс контейнера. Медиана — средний по порядку процент среди чанков; общая экономия считается по байтам. Последний чанк может быть неполным. Увеличение размера означает накладные расходы формата, а не потерю информации.

`metadata` — чанк целиком до области тензоров; `tensor_data` — целиком внутри области тензоров (она может содержать межтензорное выравнивание); `boundary` пересекает границу. Смешанный чанк не приписывается ни одной чистой области. Индекс в этой таблице не учтён. Это разбиение байтов GGUF, а не послойный формат загрузки модели.

## Данные и повторение

- [Все 80 вариантов: статистика, медиана, P95, расширение](all-levels.csv).
- [Каждый чанк восьми лучших вариантов: смещение, размеры, область](best-chunks.csv).
- [Суммы по областям](regions.csv), [граница данных GGUF](layout.json).

```sh
python3 tools/analyze_compression_chunks.py \
  --benchmark build/compression-supra-q4 \
  --source build/model-playground/supra/Supra2-100M-Instruct-Q4_K_M.gguf \
  --output build/compression-chunks-new
```

Парсер ограничен little-endian GGUF v3. Он читает структуру по [спецификации GGUF](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md); типы и значения самих весов не интерпретируются. Новых измерений RAM, скорости декодирования или inference на ESP этот анализ не содержит.
