# Нулевые и околонулевые веса наших моделей

Анализ 2026-10-18. Веса прочитаны без изменений; прунинг и проверка качества не выполнялись.

## Что это означает для хранения

Точные нули есть во всех проверенных квантованных вариантах: около 0,7–1,2%
в GGUF-кандидатах, 16,525% в PLE и 11,938% в прежней TinyTalk. В обучаемых
FP32-параметрах VaghLM и GPT-2 точных нулей не обнаружено. Маски внимания
GPT-2 с большим количеством нулей исключены: это не параметры модели.

Простая маска в 1 бит на каждый вес окупается, когда доля пропущенных значений
больше 1/b, где b — число бит на оставшееся значение: 25% для 4 бит,
16,67% для 6 бит, 12,5% для 8 бит и 3,125% для FP32. Масштабы и другая
метаинформация квантования остаются. Это условие для данной схемы, не предел
для всех алгоритмов сжатия: кодирование самой маски или блоков может дать
другой результат и здесь не измерялось.

На точных нулях схема не окупилась ни для одной модели, даже при выборе
dense/sparse отдельно для каждого тензора. Например, PLE выросла бы с
14,221 до 15,388 МиБ данных тензоров при маске на каждый тензор. Для Supra Q4:
с 62,877 до 74,096 МиБ. Заголовки и токенизаторы в эти числа не входят.

Околонулевых значений больше. Например, abs(weight) ≤ 0,01 покрывает 16,864%
Supra Q4, 34,359% PLE и 24,041% VaghLM. Если обнулить эти значения, идеальная
оценка с выбором формата по тензору даёт 0,666%, 9,584% и 20,917% экономии
данных тензоров соответственно. **Порог произвольный; сохранение качества
не проверено, это не рекомендация удалить такие веса.** Абсолютные масштабы
разных моделей и тензоров различаются, поэтому ниже есть относительный порог.

В MoE неактивный для конкретного токена эксперт не становится набором нулевых
параметров: его веса всё равно нужны для других токенов. Этот анализ не
проверяет выгрузку экспертов или ускорение sparse-операций.

## Маска и поток ненулевых значений: расчёт, не реализованный формат

## Методика и ограничения

- GGUF: восстановление значений через gguf.quants.dequantize; Supra/Stentor Q4_K_M содержат Q4_K, Q6_K и F32, Stories также Q5_0 и Q8_0. Нулевой код не приравнивается к нулевому весу.
- PLE и прежняя TinyTalk: форматы читаются по локальному коду движков; FP16 и BF16 масштабы различаются. Общий embedding/output не считается повторно.
- Vagh: только model_state, без optimizer. GPT-2: исключены причинные маски внимания; shared storage считается один раз. Список исключений сохранён в JSON.
- Считаются хранимые значения тензоров (включая обучаемые bias/norm), а не байты токенизатора и заголовков. Stories GGUF содержит 58,073,600 значений, несмотря на имя 42M.
- Проверены SHA-256 источников, конечность восстановленных значений, размеры и число параметров. Абсолютные пороги зависят от масштаба весов; относительные считаются отдельно от RMS каждого тензора.
- Нули после деквантования не обязательно были нулями до квантования. Q4/Q8 — разные представления; здесь не проверяются исходные FP32 checkpoint этих GGUF.
- Обнуление ненулевых значений меняет модель. Доля суммы квадратов удаляемых весов в JSON — численная характеристика, не оценка падения качества.
- Формат маски потребует нового декодера/kernel. Здесь не обещается ускорение, уменьшение KV-кэша или совместимость с текущей прошивкой.

## Воспроизведение

У PLE фактически прочитано 28 869 920 значений: 28 867 968 квантованных
матричных весов, как в metadata.json, плюс 1952 FP32-значения нормализаций.
У прежней TinyTalk — 9 687 808 хранимых значений. Это подсчёт данных конкретных
локальных файлов, а не округлённые названия моделей.

Для нестандартных форматов отдельно выполнена проверка с исходным кодом
прошивки: 405 значений PLE и 441 TinyTalk на первых, средних и последних
строках/столбцах всех квантованных матриц. Совпадение FP32 точное.
[Результат](native-reader-check.json), [PLE](ple-native.csv),
[TinyTalk](tinytalk-native.csv). Это выборочная проверка декодирования,
не аппаратный тест и не проверка каждой восстановленной величины.

Нативные значения получены из `tools/check_weight_readers.cpp`, собранного
через `c++ -std=c++17 -O2 -I. -DCHECK_PLE` для PLE и через
`c++ -std=c++17 -O2 -I. -Icomponents/tinytalk/include -Itools/host` для TinyTalk.
Параметр исполняемого файла — путь к соответствующему model.bin. Сравнение
делалось с Python-readers `ple_tensors` и `tinytalk_tensors` при точном равенстве.

```sh
python -m pip install 'gguf==0.19.0' 'numpy==2.2.6' 'torch>=2.6'
python tools/analyze_weight_sparsity.py --output build/weight-sparsity-new
```

Нужны уже скачанные модели по путям из report.json. На этом Mac использовано существующее Torch-окружение с gguf из build/compression-venv310 через PYTHONPATH. Анализ не скачивает веса.

[JSON с источниками и оценками всех порогов](report.json), [по каждому тензору](tensors.csv).

Реализация деквантования: [официальный gguf-py](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/quants.py).
