# UART0 phase0-патч и ошибка открытия порта — 2026-10-18

**Исторический перенос в `4b78e2c`. Текущее исправление для native USB описано
[ниже](#обновление-по-новому-логу-пользователя).**

Пользователь передал `phase0-uart0-console.patch` и запросил его применение.
[Оригинал сохранён](patches/phase0-uart0-console.patch). Прямой `git apply --check`
отвергает его, потому что здесь нет Arduino-файлов `firmware/esp32_tinystories/`.
Вместо добавления второго несобираемого проекта перенесены изменения в текущий
ESP-IDF-порт.

| Изменение патча | Реализация в tinyMl |
| --- | --- |
| Native USB + UART0 115200 | UART0 остаётся primary; `CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG=y` зеркалирует вывод на native USB |
| Вывод всех сообщений и токенов на UART0 | `printf`/`fputs` идут через primary ESP-IDF console, включая диагностику и сгенерированный текст |
| Работа без OLED | Уже была однократная I2C-проба; при отсутствии дисплея отрисовка ничего не отправляет |
| Фактическое наличие дисплея | `display_is_present()` и `display_present` в `/stats` и benchmark; после ошибки отрисовки значение станет false |
| Признак двухъядерной работы и профиль | Уже присутствовали `dual_core`, `profile`, `[timing]` и `[profile ms/token]` |
| Повторный замер | Существующий `/bench` запускает тот же фиксированный 200-токенный прогон без перезагрузки; `/bench oled` включает экран |

Native USB — дополнительный **выход**. Команды вводятся через основной UART0,
соединённый с USB–UART-мостом платы. Это соответствует требованию сохранить
USB-общение на используемом разъёме. ESP-IDF поддерживает такую маршрутизацию
через [secondary console](https://github.com/espressif/esp-idf/blob/v6.1/components/esp_stdio/Kconfig).
Проверен и локальный исходный `stdio_vfs.c`: результат записи в дополнительный
канал не заменяет результат записи в основной UART. Режим USB использует
штатный ограниченный по ожиданию путь ESP-IDF; влияние зеркала на скорость
ещё нужно измерить на ESP, особенно при подключённом native USB без читателя.

`tools/configure_uart0.py` мигрирует существующий sdkconfig: defaults сами по
себе его не переопределяют. Другие настройки сохраняются, исходный файл
копируется с уникальным суффиксом `.before-uart0-*`; повторный вызов не создаёт
копию, если изменений уже нет. Тесты миграции написаны и запущены до применения
к локальной сборочной конфигурации.

## Подтверждено локально

- Два теста миграции: UART0/native mirror, сохранение пользовательских настроек,
  резервной копии, идемпотентность и создание новой конфигурации — прошли.
- `python3 tools/check_host.py` — прошёл после изменения вывода диагностики.
- ESP-IDF v6.1 build для ESP32-S3 — прошёл. Приложение 645 344 байта, модель

## Ошибка пользователя: пока не воспроизведена здесь

Лог пользователя:

```text
Running idf_monitor in directory /home/espdev/test
... /home/espdev/test/build/tinyml.elf ... /home/espdev/test/build/test.elf ...
--- Connection to /dev/ttyACM0 failed. Available ports:
...
--- /dev/ttyACM0
[Errno 71] Protocol error
```

Подтверждён сбой открытия порта; ни загрузка модели, ни скорость на ESP этим
логом не проверены. `EPROTO` относится к USB-ошибкам; один такой код не позволяет
отличить проблемы устройства, соединения и драйвера. Это ограничение описано
в [документации ядра Linux](https://cdn.kernel.org/doc/html/latest/driver-api/usb/error-codes.html).
Причина для этой платы **не установлена**, исправление `Errno 71` не подтверждено.
Доступа к Linux-хосту и плате у агента нет. Полный цикл воспроизведения поэтому
ждёт пользовательского лога; тест на Mac не может заменить его.

Запросить журнал `sudo dmesg --ctime | tail -80`, `lsusb` либо результат
`python tools/diagnose_usb.py /dev/ttyACM0` из активированной среды ESP-IDF.
Последняя команда проверяет порт через тот же pyserial, печатает traceback
конкретной операции и сохраняет USB-сведения вместе с журналом ядра.
Если порт занят, она сообщит об этом и не будет завершать чужие процессы.

Использовать `-B build/esp32ai` последовательно для build/flash/monitor:
в исходном логе выбран другой каталог `build`. Это отдельное обнаруженное
расхождение, а не доказанная причина `EPROTO`.

## Обновление по новому логу пользователя

Пользователь выполнил диагностику на `4b78e2c`. Получены:

```text
USB idVendor=303a
USB idProduct=1001
USB product=USB JTAG/serial debug unit
Driver: /sys/bus/usb/drivers/cdc_acm
PASS: port opened and serial settings applied.
First bytes: b''
```

Это **native USB ESP32**, не ранее описанный CH343. Предыдущий совет использовать
UART0 для этого подключения был ошибочным: secondary USB даёт лишь выход,
поэтому пользователь не сможет вводить команды через подключённый разъём.
Это самостоятельная подтверждённая ошибка маршрутизации; она не объясняет
задним числом прежний `Errno 71`.

В новом тесте ошибка открытия не воспроизвелась. В присланном фрагменте `dmesg`
видны обнаружение `303a:1001`, один disconnect/reconnect и повторное подключение
`cdc_acm`; причины отключения из этих строк не видно. Строки AppArmor Firefox и
UFW относятся к другим подсистемам. Пустое чтение за одну секунду не доказывает
ни исправность, ни сбой модели: программа могла ждать ввода или уже вывести
стартовые сообщения до открытия монитора. Новых гипотез о неисправном кабеле,
драйвере или firewall без воспроизведения EPROTO не утверждаем.

### Исправление

- Defaults выбирает **primary** `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`,
  secondary выключен. Выбор основан на VID:PID, не на имени ttyACM.
- `tools/configure_console.py ... --interface usb` исправляет существующие
  настройки с резервной копией. `--interface uart0` и старый helper оставлены
  для реального USB–UART-моста; прочие настройки платы сохраняются.
- При primary USB приложение устанавливает штатный interrupt-driven драйвер
  через `esp_stdio_install_io_driver()`. Это обеспечивает ввод и отправку
  коротких фрагментов без ожидания newline/полного FIFO. Именно такое различие
  режимов описано в установленной документации ESP-IDF v6.1:
  `docs/en/api-guides/usb-serial-jtag-console.rst`, раздел Data Buffering.
- Для этого драйвера явно подключён компонент `vfs` и включён
  `CONFIG_VFS_SUPPORT_IO`. Проверка промежуточного ELF выявила отсутствие VFS:
  установка драйвера возвращала бы `ESP_ERR_NOT_SUPPORTED`. Зависимость исправлена
  до отправки пользователю, а такая конфигурация теперь останавливает компиляцию.
  `tools/check_usb_build.py` проверяет наличие реальных USB RX/TX функций в ELF,
  чтобы успешная линковка с заглушкой больше не считалась достаточной проверкой.
- `/stats` явно печатает фактический канал ввода и вывода.

### Проверка

Регрессионный тест defaults сначала упал на версии с UART0:
`303a:1001 needs PRIMARY USB; the secondary mirror cannot receive commands`.
После исправления прошли два новых теста выбора USB/миграции туда-обратно и
два прежних теста UART0. Host-проверки прошли; local ESP-IDF build и проверки
конфигураций приложения/bootloader зафиксированы в
[native-usb-build-receipt.json](evaluation/esp32ai/native-usb-build-receipt.json).
Это локальные проверки, **не тест общения через USB на плате**.

Следующий шаг пользователя: обновить репозиторий, выполнить configure с
`--interface usb`, затем build/flash/monitor в `build/esp32ai`. После `[READY]`
ввести `/stats` и `/bench`. При отсутствии стартового вывода нажать RESET/EN
при открытом мониторе; прислать полученный boot-лог.
